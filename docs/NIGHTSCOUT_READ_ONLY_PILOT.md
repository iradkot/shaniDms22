# Nightscout access for the pilot

New native and browser connections require a persistent Nightscout subject access token. In Nightscout Admin, the site owner creates a separate subject with only the `readable` role, then copies its access token into ShaniDms. Keep the master `API_SECRET` in the owner's control. A pasted `token=` prefix is accepted; a token embedded in a URL, master secret, SHA1 master-secret hash, or temporary JWT is not accepted for a new connection.

ShaniDms calls `GET /api/v2/authorization/request/{accessToken}` and inspects the returned `permissionGroups`, which contain the subject's roles **and the site's default roles**. It accepts only read grants covering entries, treatments, profile, devicestatus and status. Wildcard actions, write grants, explicit admin grants, malformed groups, and unknown grant syntax fail closed. A site whose default roles grant treatment writes also fails this check. The app then reads actual sensor glucose entries; a public status endpoint alone cannot establish success.

The persistent token is never hashed. Native and Android background/widget GET requests send it unchanged in the `api-secret` header, which Nightscout explicitly supports for subject tokens. The old browser compatibility adapter uses the documented `token` query parameter. The rebuilt browser uses ShaniDms' authenticated stateless proxy and receives no vaulted credential. The backend uses the same raw-token header, pins a public DNS answer, denies redirects, and performs the same permission and glucose checks before vault provisioning.

Device tokens remain in the account-scoped Keychain/Keystore store; only the credential kind is added to ordinary profile metadata. The Android bridge retains its existing encrypted Keystore format. Vault credentials remain encrypted with account-bound authenticated encryption. Existing account-scoped API_SECRET profiles retain their IDs, Workspaces and data, remain distinguishable as legacy connections, and display a reconnect notice. They are never described as having verified read-only permissions. Existing owned server legacy credentials can be re-provisioned only without changing the URL or secret. A local legacy credential that has never reached the server requires token reconnection to start backend/browser use.

Revoked tokens fail verification without an anonymous-read fallback. A missing secure device credential disables source/background configuration. Changing accounts clears configured headers/query parameters and disables the previous background source. Permission verification is repeated when a token connection is tested, added, edited or provisioned. This does not freeze permissions in the external Nightscout site: its owner can change roles later, and ShaniDms itself continues to issue GET requests only. No site roles, secrets, or external configuration are changed by this implementation.

Automated tests cover raw-token transport, secure account separation and restart, browser proxy provisioning, Android bridge compatibility, permission rejection including default-role writes, revoked tokens, safe errors, and legacy preservation. A real site connection, token revocation, background refresh, and account switching still require the device acceptance test recorded in the pilot verification report.

Account deletion records opaque cache-source identities before removing connection metadata. Owner-scoped source and credential-service indexes retain attribution for removed profiles and interrupted saves. Deletion drains in-flight credential and cache writes, blocks later writes from old async operations, and removes only that owner's indexed connections and caches. Historical opaque caches left by profiles removed before these indexes existed cannot be safely attributed to an account. Range caches are pruned under their 14-day policy during cache operations; old Oracle caches have no guaranteed automatic expiry. This implementation does not claim complete deletion of unassignable pre-upgrade local remnants.
